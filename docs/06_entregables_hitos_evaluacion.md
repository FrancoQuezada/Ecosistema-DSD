# Entregables, hitos y evaluación

El taller evalúa proceso y resultado. La evaluación no debe concentrarse solo en la presentación final, sino considerar evidencia semanal, avance incremental, decisiones de diseño, implementación, validación, documentación y potencial de continuidad.

## Entregables semanales

| Semana | Entregable principal |
|---:|---|
| 1 | Ficha inicial del proyecto, roles y solución preliminar |
| 2 | Propuesta de valor, caso de uso principal, repositorio y README inicial |
| 3 | Backlog priorizado, historias de usuario, criterios de aceptación y primer avance con IA |
| 4 | Flujo de usuario, wireframes, mapa de pantallas y prototipo navegable |
| 5 | Diagrama técnico, stack definido, ambiente documentado y despliegue temprano |
| 6 | Modelo de datos, diccionario básico, matriz de riesgos y conexión inicial con datos |
| 7 | Flujo principal parcialmente funcional y bitácora de IA actualizada |
| 8 | Demo alpha, backlog corregido y plan de implementación |
| 9 | Operación principal implementada, manejo de errores y registro de pruebas manuales |
| 10 | Matriz de seguridad y privacidad, reglas de acceso y ajustes implementados |
| 11 | Plan de pruebas, registro de bugs y backlog de correcciones |
| 12 | Reporte de validación, evidencia de feedback y MVP beta ajustado |
| 13 | Matriz ética, análisis de adopción y condiciones de continuidad |
| 14 | MVP desplegado o reproducible, README completo, guía de uso y roadmap |
| 15 | Pitch preliminar, demo final candidata y material de apoyo |
| 16 | Pitch final, demo pública, repositorio, documentación y ficha de continuidad |

## Hitos principales

| Hito | Semana | Resultado esperado |
|---|---:|---|
| Hito 0 | 2 | Repositorio, editor y flujo GitHub funcionando |
| Hito 1 | 4 | Prototipo navegable construido con apoyo de IA |
| Hito 2 | 6 | Arquitectura, datos iniciales y despliegue temprano |
| Hito 3 | 8 | Demo alpha del flujo principal |
| Hito 4 | 12 | MVP beta validado preliminarmente |
| Hito 5 | 15 | Demo final y pitch ensayados |
| Final | 16 | Presentación pública ante actores clave |

## Paquete final del proyecto

Al cierre del curso, cada equipo debe entregar:

1. Presentación final o pitch deck.
2. Demo funcional.
3. Repositorio GitHub.
4. README completo.
5. Documentación funcional.
6. Documentación técnica.
7. Modelo de datos.
8. Matriz de riesgos de datos, seguridad y privacidad.
9. Bitácora de uso de IA.
10. Plan de pruebas y registro de bugs.
11. Reporte de validación.
12. Matriz ética e impacto.
13. Ficha de continuidad.
14. Roadmap de mejoras.
15. Enlace a despliegue o instrucciones para ejecutar la demo.

## Criterios de evaluación sugeridos

### 1. Valor y pertinencia de la solución

Evalúa si el MVP responde a un desafío relevante y si la propuesta de valor está claramente formulada.

Aspectos observables:

- claridad del usuario objetivo;
- conexión entre problema, solución y valor;
- relevancia del caso de uso principal;
- coherencia entre desafío y MVP.

### 2. Definición y gestión del MVP

Evalúa la capacidad del equipo para acotar, priorizar y construir una solución viable.

Aspectos observables:

- backlog priorizado;
- historias de usuario;
- criterios de aceptación;
- control de alcance;
- decisiones explícitas sobre qué queda dentro y fuera del MVP.

### 3. Diseño UX/UI

Evalúa si la solución es comprensible, usable y coherente con el flujo principal.

Aspectos observables:

- claridad del flujo de usuario;
- consistencia de pantallas;
- facilidad de navegación;
- calidad de formularios;
- accesibilidad mínima;
- diseño orientado al usuario.

### 4. Arquitectura y desarrollo técnico

Evalúa la calidad mínima de la implementación y la coherencia técnica.

Aspectos observables:

- estructura del proyecto;
- componentes funcionales;
- integración entre frontend, lógica y datos;
- uso adecuado de repositorio;
- despliegue o reproducibilidad;
- documentación técnica;
- manejo básico de errores.

### 5. Datos, seguridad y privacidad

Evalúa si el equipo identifica y gestiona adecuadamente la información necesaria para el MVP.

Aspectos observables:

- modelo de datos;
- diccionario de datos;
- minimización de datos;
- identificación de datos sensibles;
- reglas de acceso;
- matriz de riesgos;
- manejo de variables y secretos.

### 6. Uso crítico y trazable de IA

Evalúa si el equipo usa IA como apoyo efectivo, no como sustituto de criterio técnico.

Aspectos observables:

- bitácora de IA;
- prompts o tareas documentadas;
- revisión humana;
- modificaciones al código generado;
- commits verificables;
- identificación de errores o límites de la IA.

### 7. Validación y calidad

Evalúa si el MVP fue probado y mejorado a partir de evidencia.

Aspectos observables:

- plan de pruebas;
- registro de bugs;
- pruebas entre pares;
- feedback de usuarios o stakeholders;
- mejoras priorizadas;
- evidencia de iteración.

### 8. Ética, impacto y adopción

Evalúa si el equipo comprende las consecuencias y condiciones de uso real del MVP.

Aspectos observables:

- matriz ética;
- análisis de beneficiarios y riesgos;
- accesibilidad;
- privacidad;
- sesgos;
- stakeholders;
- condiciones para piloto;
- continuidad.

### 9. Comunicación y presentación

Evalúa la capacidad del equipo para comunicar el valor del producto a actores técnicos y no técnicos.

Aspectos observables:

- claridad del pitch;
- calidad de la demo;
- evidencia de resultados;
- narrativa de valor;
- respuestas ante preguntas;
- identificación de próximos pasos.

## Evaluación por actores invitados

En la presentación final, los actores invitados pueden evaluar el potencial de los proyectos mediante una pauta breve.

Criterios sugeridos:

- claridad del problema abordado;
- valor de la solución;
- funcionalidad del MVP;
- facilidad de uso;
- factibilidad técnica;
- impacto potencial;
- riesgos identificados;
- pertinencia para un piloto;
- interés en continuidad o colaboración.

## Escala simple sugerida para evaluación externa

| Puntaje | Interpretación |
|---:|---|
| 1 | Bajo potencial o propuesta poco clara |
| 2 | Potencial limitado; requiere redefinición importante |
| 3 | Potencial medio; requiere mejoras relevantes |
| 4 | Buen potencial; podría avanzar con ajustes |
| 5 | Alto potencial; recomendable explorar continuidad |

## Evidencia mínima para aprobar el taller

Un equipo debería demostrar, al menos:

- un MVP funcional o demo reproducible;
- repositorio actualizado;
- documentación mínima;
- uso de IA documentado;
- modelo de datos o estructura de información;
- matriz de riesgos;
- validación preliminar;
- presentación final.
